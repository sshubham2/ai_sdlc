# ADR-066: Track the AI SDLC vault (`architecture/`) in git to enable cross-machine parallel slice development and structurally retire the N=4 worktree-vs-gitignored-vault class

> **Supersession scope** (per /critique B3 ACCEPTED-FIXED): this ADR partially supersedes [[ADR-028]] §Options-#1 ("Un-gitignore the vault — rejected (deliberate `.gitignore:11`; scoped out)"). ADR-028's Option-1 rejection was a *scoped-out deferral* limited to slice-030A's BC-1-vault-repair scope (its concern was the canonical-fixture pin, not the tracking discipline). ADR-066 reframes the decision at the methodology-architecture level: now that BCI-1 ([[ADR-029]]) provides a tracked oracle for the live build-checks file AND `VAULT_ROOT` ([[ADR-065]]) provides the rename seam, the original 030A-era scope-out is addressable on its own merits. The BCI-1 core of ADR-028 (Decisions 1-3: tracked fixtures + literal-constant oracle + full-structural-identity gate) remains **accepted unchanged**; only the §Options-#1 rejection is revisited. Frontmatter `supersedes: null` reflects that ADR-028 stays accepted; the partial scope-supersession is documented in this prose block + Options §Option 1 (revised) below.

## Context

Since this repository's adoption of the AI SDLC pipeline (2026-05-13), the `architecture/` vault directory has been gitignored per the `.gitignore:11` rule with the line-10 comment `# Local-only AI SDLC vault (per-project; never tracked)`. The vault holds the methodology archive: every ADR (065 to date), every slice folder (068 archived + 18 from the original adoption + ongoing), the risk register (R-1 through R-17 + active risks), the methodology-changelog (v0.0.0 through v0.69.0), build-checks, shippability catalog, candidate queue, lessons-learned, principles, pipeline doc, tutorial. ~11MB / hundreds of files.

The "Local-only" posture was inherited from the AI SDLC methodology's brownfield-adoption defaults (the upstream `~/.claude/ai-sdlc-VERSION` ships a `.gitignore` template that ignores the vault by default — appropriate for *first-encounter* repos where the vault content is sensitive and bootstrapped per-machine). For *this* repository — which IS the AI SDLC methodology source and dogfoods its own pipeline — that default has become two distinct sources of friction:

1. **Cross-machine parallel development is impossible.** The user surfaced this directly via `/query-design` 2026-05-25: the next natural slice candidate (`add-slice-queue-claim-state-machine`) targets parallel slice development, but parallel REMOTE development requires the slice-queue + candidate sources to be visible across machines. Today, slice candidates live in `architecture/risk-register.md` + `architecture/slices/_index.md` + `architecture/slices/archive/*/reflection.md` + `architecture/slice-queue.md` + `diagnose-out/backlog.md`. All of `architecture/` is gitignored. A second machine (laptop, CI runner, fork-collaborator) cannot see any candidates — every cross-machine session would start blind and have to manually rebuild the vault state.

2. **BRANCH-2 worktree-per-slice (ADR-063) accumulates a recurring tax** of `cp -r architecture/ diagnose-out/ graphify-out/` DEVIATION lines. The pattern fires every time a slice runs in a BRANCH-2 worktree AND depends on vault state via `tests/methodology/conftest.py` `_resolve_slice_dir(NNN)` or module-level `REPO_ROOT / "architecture"` resolution: `git worktree add` creates the worktree from git-tracked content only, so the gitignored vault doesn't propagate, so the worktree's tests cannot find slice folders, so the slice paid a `cp -r` DEVIATION tax to seed the worktree. Witnessed N=4 cumulative: slice-067 (the first BRANCH-2-governed slice, `WORKTREE=skip` fallback used), slice-068 (`cp -r` DEVIATION), and pre-067 implicit precursors in the pattern's discovery sequence. Slice-068's `/reflect` explicitly nominated this slice as the structural fix.

A third motivation is **vault-as-history**: forks of this methodology repo would benefit from the methodology's own slice-by-slice development trail being visible — every ADR was minted in a specific slice with a specific Builder + Critic + Builder-revision lineage, and that lineage is part of the methodology's value. A gitignored vault hides that history from anyone not on the original machine.

## Options considered

1. **Status quo — keep `architecture/` gitignored, per [[ADR-028]] §Options-#1 rejection (slice-030A, 2026-05-16).** The prior rejection's rationale was a `"scoped out"` deferral for the BC-1 vault-repair slice (030A's focus was the canonical-fixture pin, not the tracking discipline). Adopting Status quo would honor that deferral indefinitely. Pros: zero work; no large initial commit; vault content stays per-machine private (low secret-exposure surface); honors the explicit ADR-028 §Options-#1 rejection. Cons: cross-machine parallel development blocked; N=4 worktree-vs-gitignored class continues accumulating tax on every BRANCH-2 slice; methodology-as-history hidden from forks/collaborators; the slice-068 reflection's "accelerate slice-069 as the structural fix" finding remains unaddressed; the ADR-028 deferral was scope-limited to slice-030A's BC-1-vault-repair concern, NOT a permanent posture lock — re-evaluating at the methodology-architecture level is exactly what slice-069 is for.

2. **Track all of `architecture/` in git (this ADR).** Pros: cross-machine parallel development enabled (any machine running `git clone` + `git pull` has the full vault visible); N=4 class structurally retired (BRANCH-2 worktree creation propagates the vault automatically); methodology-as-history is git-visible for forks. Cons: ~11MB initial commit (permanent repo size growth); secret-exposure surface reframed (any future ADR / slice / reflection containing a secret would be irrevocably committed unless caught by pre-commit secrets scan); contributors must clone+pull rather than bootstrap their own vault.

3. **Track only the load-bearing subset of `architecture/`** (e.g., risk-register + slices/archive/_index.md + methodology-changelog only; keep slice folders + ADR files gitignored). Pros: smaller initial commit; less secret-exposure surface. Cons: defeats motivation #1 (cross-machine candidate sources need slice folders + ADRs to be visible — Aggregated lessons, archived reflections, candidate metadata all live in slice folders); defeats motivation #3 (history truncated to indexes, not full lineage); creates a confusing partial-tracking discipline that future maintainers must remember; the .gitignore rule list grows complex.

4. **Move the vault to a separate git submodule.** Pros: clean separation of methodology code vs methodology archive; submodule update can be opt-in per consumer. Cons: **breaks the dogfood premise that this *one* repo IS the methodology** (this is the load-bearing rejection — the self-hosting discipline requires the methodology source AND the methodology archive to live in the same repo); massive operational complexity follows from the dogfood-break (submodule init/update gymnastics on every checkout; CI must propagate submodule; first-time forkers face a confusing 2-repo bootstrap; for collaborators not on the original machine, the submodule needs its own remote which doubles infrastructure).

5. **Move the vault to `.sdlc/` AND track it (the user-named candidate, bundled).** Pros: enables cross-machine + naming convention matches the user's stated "AI SDLC" branding intent. Cons: SCOPE — the rename half alone is LARGE (~480 occurrences across ~73 files: 24 SKILL.md + 4 agents + CLAUDE.md + 48 test files + 42 tools files + tutorial.md + pipeline.md); combining with the tracking half violates the ≤1 day per-slice scope hard limit at `/slice` Step 5; explicitly split into slice-069 (this — tracking only) + slice-070 (rename, after this ships) per the structured-options scope decision at `/slice` 2026-05-25.

## Decision

Adopt **option 2**: remove `architecture/` from `.gitignore` (line-11 deletion + line-10 comment revision to describe the new tracked discipline) and commit the entire `architecture/` tree on slice-069's slice branch. Keep `graphify-out/` (entirely derived, regenerable via `$PY -m graphify code .`) and `diagnose-out/` (mostly derived; `backlog.md` is load-bearing for BCR-1 but its cross-machine tracking is a separate decision deferred from this slice) gitignored.

- **Tracked scope**: all of `architecture/` (`decisions/`, `slices/`, `slices/archive/`, `risk-register.md`, `methodology-changelog.md`, `lessons-learned.md`, `build-checks.md`, `shippability.md`, `concept.md`, `triage.md`, `principles.md`, `pipeline.md`, `tutorial.md`, `slice-queue.md`).
- **NOT tracked** (this slice): `graphify-out/`, `diagnose-out/` (any file under), `__pycache__/`, `*.pyc`, `*.pyo`, `.pytest_cache/`, `.claude/`. The `.gitignore` lines 1-7 + 16-17 preserve these.
- **Naming preserved**: directory stays `architecture/`. The rename to `.sdlc/` is slice-070 scope (1-line `_DEFAULT` flip in `tools/_vault_paths.py` per slice-068's seam, plus the ~480-occurrence prose+test sweep).
- **`tools/_vault_paths.py` constant preserved**: `_DEFAULT = "architecture"` unchanged; the slice-068 seam's consumer-freeze cascade contract is unaffected.
- **BCI-1 contract preserved**: the live-vs-fixture dual-source contract for `architecture/build-checks.md` ≡ `tests/methodology/fixtures/build_checks/canonical_project_checks.md` stays. Both files happening to be co-tracked is an improvement (drift becomes PR-visible at review time before BCI-1 fires), not a defect.
- **SCMD-1 contract preserved**: the incidental-decoupling invariant's runtime check continues to pass (the cited-fn set is unchanged); the "incidental" naming becomes a historical artifact rather than active enforcement, but the audit's semantics are unaffected.
- **Pre-commit secrets scan + PII redaction sweep**: must-not-defer per slice-069 mission-brief. Per /critique B1 ACCEPTED-FIXED, the secrets scan invokes the canonical `tools/validate_slice_layers.py` `_SECRET_PATTERNS` (9 production patterns: AWS / GitHub PAT / Slack / JWT / RSA / Anthropic / OpenAI / generic-api-key / BEGIN-PRIVATE-KEY) against every `.md` / `.txt` file under `architecture/` — NOT a hand-rolled grep (the original hand-rolled grep empirically matched zero of 4 real secret shapes at /critique time, exit=1). Per /critique B2 ACCEPTED-PENDING, a separate PII redaction sweep handles the absolute-path / GitHub-handle / personal-project-name class (pre-flight count at /critique time: 93 unique `<HOME>\...` paths in `architecture/`, including the unrelated `<private-project>` private project leak); mechanical `sed`-substitute `<HOME>\` → `<HOME>\` and `<github-user>` → `<github-user>`, re-verify pytest 944 baseline post-redact.

## Consequences

- **Cross-machine parallel slice development enabled.** Any second machine running `git clone <this-repo> + git pull` has the full vault visible. `/slice` reads risk-register, slice archive, lessons-learned, candidate queue — all of which are now git-tracked. The user's `/query-design` 2026-05-25 motivating concern is structurally resolved.

- **N=4 cumulative worktree-vs-gitignored-vault class retired.** Future BRANCH-2 slices' `git worktree add` propagates the vault content automatically (since it's now tracked). The `cp -r architecture/` DEVIATION pattern no longer needs to fire. The `WORKTREE=skip` escape-hatch stays available for legitimate bootstrap cases (slice-066 minted the discipline; slice-067 was the first governed slice's structural-conflict precursor) but the recurring tax is gone.

- **Repo size grows permanently by ~11MB.** Mostly text (ADRs, reflections, methodology-changelog), highly compressible in git's delta storage. Future commits add slice folders + ADR files + reflection.md content as normal git deltas — typical slice adds ~50-500KB.

- **Secret-exposure surface reframed.** Future ADRs / slice folders / reflections / lessons that accidentally contain a secret (API key, credential, personal data) would be irrevocably committed to git history unless caught by the pre-commit secrets scan (must-not-defer this slice + every future slice via inheritance). Mitigation: the canonical VAL-1 `tools/validate_slice_layers.py` `_SECRET_PATTERNS` (9 production patterns) is the gate, NOT a hand-rolled grep — the original hand-rolled grep proposed in mission-brief v1 empirically matched zero of 4 real secret shapes at /critique time and was replaced per /critique B1 ACCEPTED-FIXED. Future slices inherit the VAL-1-backed gate; future extensions to `_SECRET_PATTERNS` propagate to vault-scan automatically without slice-level work.

- **Forks become methodology-as-history**. Anyone forking this repo gets the full slice-by-slice development trail of the methodology itself — every ADR's Critic + Builder + Builder-revision lineage is visible, every retirement of a deferred slice is traceable, every methodology-changelog v0.NN.0 entry has its slice's full vault behind it.

- **Slice-070 becomes tractable**: the rename `architecture/` → `.sdlc/` is now possible without the cross-machine-parallel-development motivation (which is retired by THIS slice). Slice-070 becomes purely a naming-convention slice with the user's discretion on timing; it may even be deferred indefinitely if the `architecture/` name turns out fine in practice.

- **BCR-1 cross-machine partial**: `/slice` running on a second machine sees the tracked vault sources but does NOT see `diagnose-out/backlog.md` (still gitignored). For full cross-machine BCR-1, `diagnose-out/backlog.md` would need its own tracking decision (separate slice, separate ADR). This slice deliberately leaves that decision for later — partial cross-machine BCR-1 (4-of-5 sources visible) is better than the previous zero-of-5.

- **The slice-069 folder itself becomes tracked at slice ship time**: `architecture/slices/slice-069-track-vault-in-git/` and all its artifacts (mission-brief.md, design.md, this ADR, critique.md, critique-review.md, build-log.md, validation.md, reflection.md) land in the vault commit as part of the normal slice lifecycle. This is the dogfood: slice-069 ships its own evidence inline.

- **Implicit "vault is local-only" cultural premise retired.** Any future slice / ADR / reflection / methodology-changelog entry that mentions vault being "Local-only" / "gitignored" / "never tracked" as a load-bearing premise is now incorrect prose that should be revised. This slice promotes the most-active stale-prose surface (`skills/code-review/SKILL.md:66` `architecture/**` exclusion — per /critique M5 ACCEPTED-PENDING) into slice-069 build scope; the remaining 3-4 less-active surfaces (`methodology-changelog.md`, `skills/build-slice/SKILL.md`, `skills/validate-slice/SKILL.md`, `skills/reflect/SKILL.md`, `tests/methodology/fixtures/build_checks/canonical_project_checks.md`) are deferred to slice-070 per design.md §Sites EXCLUDED.

- **BC-PROJ-8 evergreen rule promoted into slice-069 build scope** (per /critique B4 ACCEPTED-PENDING): the rule's `Check` text literally asserts the vault is gitignored as the structural-impossibility premise. Once slice-069 ships, that premise is false. Slice-069 build scope revises BC-PROJ-8's `Check` + `Rationale` + `Trigger keywords` (drop `"gitignored"`) on BOTH the live `architecture/build-checks.md` AND the canonical fixture `tests/methodology/fixtures/build_checks/canonical_project_checks.md`, sweeps the ~12 literal-constant pin references in `tests/methodology/test_build_checks_audit.py` (`test_bc_proj_8_has_expected_structural_identity` + the integrity-test fixtures), and adds a methodology-changelog supersession note. BC-PROJ-8's *intent* (vault-targeting tools should prefer live-file reads over git-history reads for cross-machine-safety reasons) remains coherent; only the structural-impossibility framing changes. Estimated +0.25 day; documented as in-band fix, not deferred.

- **STP-1 docstring stale-rationale sweep promoted into slice-069 build scope** (per /critique B5 ACCEPTED-PENDING): `tools/state_transition_pin_audit.py:28-37` Sub-form B docstring asserts `"architecture/ is gitignored so the merge-base form was inapplicable"` as the design rationale. Slice-069 build scope revises the docstring to reframe Sub-form B as a *choice* (the git-independent standing-invariant approach remains correct; the gitignored-vault was the original *cause* but post-slice-069 the choice is now a *preference* — fewer git-subprocess calls + works on shallow clones); methodology-changelog entry pin at `tests/methodology/test_methodology_changelog.py:3060` updated alongside. Estimated +0.1 day.

- **Co-tracking introduces three new BCI-1 failure modes** (per /critique B6 ACCEPTED-FIXED + /critique-review M-add-1 ACCEPTED-FIXED):
  1. **Corruption-on-master window**: pre-slice-069, an `/reflect` Step 5b drift of `architecture/build-checks.md` was a *local* corruption (R-4 class); BCI-1 caught it at the next `/build-slice`. Post-slice-069, the same drift becomes a *commit-staged* corruption — a slice that drifts build-checks AND bypasses BCI-1 (e.g., `--no-verify` or a slice that skips Step-6 audits) ships corrupt build-checks to master. Mitigation: BCI-1 remains a Step-6 non-opt-out pre-finish gate, which catches the drift before `/commit-slice --merge`; the corruption-on-master scenario requires DOUBLE failure (drift + audit bypass), strictly stricter than the previous single-failure path. Net posture: more resilient, not less.
  2. **Parallel-branch merge-conflict on machine-generated artifact**: two slices on parallel BRANCH-2 branches that each invoke `/reflect` Step 5b create a 3-way merge conflict on `architecture/build-checks.md`. Pre-slice-069 this was impossible (live file gitignored, untracked, no merge). Mitigation: each `/reflect` slice's diff is small (one rule promotion at most); the canonical-fixture-driven reconstruction makes manual resolution mechanical (re-run BCI-1's reconstruction); slice-070+'s remote-cross-machine-slice-claim-semantics work (queued in slice-queue.md) addresses parallel-branch coordination broadly. Document this in the BRANCH-2 cross-machine extension when it ships.
  3. **Inadvertent `git rm` of tracked live file** (per /critique-review M-add-1): pre-slice-069 the live file was gitignored — "absent" could only mean "never authored / locally corrupt" (R-4 class). Post-slice-069 "absent" can also mean "git-removed by accident in commit X by an unrelated slice that touches the vault". `tools/build_checks_integrity.py` HALTs with exit 1 on project-live absent (the correct fail-loud posture), but the recovery path differs: `git revert` of the rm commit (not a fixture-driven reconstruction). Mitigation: BCI-1's Step-6 non-opt-out pre-finish posture catches the rm in the SAME slice that introduces it (the rm cannot reach master without bypassing Step-6 BCI-1 explicitly); the failure mode is single-slice-bounded, not master-corruption.

- **Secrets-scanning posture is single-pattern-set / one-shot, NOT layered-defense** (per /critique-review M-add-2 — trade-off-naming gap): VAL-1's `_SECRET_PATTERNS` covers 9 high-value modern shapes (AWS / GitHub PAT / Slack / JWT / RSA / Anthropic `sk-ant-` / OpenAI `sk-...T3BlbkFJ...` / generic `api_key=` / `BEGIN PRIVATE KEY` block). Industry baselines like `gitleaks` ship 150+ patterns and the layered-defense pattern (pre-commit hook + CI scan + periodic full-history rescan) is standard practice (GitGuardian 2026 SoSS reports ~28M secrets leaked to public GitHub in 2025). Slice-069's posture is one-shot-pre-commit-only via VAL-1, NOT a full `gitleaks` integration. **The trade-off is accepted because**: (a) this repo is the methodology source, not a multi-developer collaboration target with frequent secret-handling code; (b) the 9 VAL-1 patterns cover the threat classes most likely to appear in vault prose (ADRs / reflections / methodology-changelog mention `api_key` / `sk-ant-` / `ghp_` shapes in security discussions and AC contexts, not in actual credentials); (c) adopting `gitleaks` is a separate future slice with its own threat-model + dependency-add decision. Future extensions to `_SECRET_PATTERNS` (or layering a `gitleaks` pre-commit hook for defense-in-depth) is a follow-up slice nominee; slice-069 ships with the documented limitation, not a hidden-assumption gap.

- **Operational scaling of the largest commit in repo history** (per /critique M6 ACCEPTED-FIXED): slice-069's `/commit-slice --merge` is the operationally riskiest merge in this repo's history (~11MB / ~631 files / hundreds of insertions per file). A pre-`--merge` dry-run is must-not-defer (mission-brief §Pre-finish gate item). Specifically: (a) `git diff --cached --stat | tail -5` after `git add architecture/` to confirm staged diff is sane; (b) confirm `/commit-slice` pre-flight audits (BCI-1, SCMD-1, PMI-1, etc.) pass against the staged state — these audits' first encounter with a *tracked* `architecture/` is at this very commit, and may surface latent contracts (e.g., the slice-069 folder's own `architecture/slices/slice-069-track-vault-in-git/` becomes part of `slices/_index.md` enumeration); (c) `git merge --no-ff` of 631-files into master is a multi-second operation but well within git's design envelope; BRANCH-2 worktree-remove (per [[ADR-063]]) order-load-bearing rules unaffected.

## Reversibility

**Expensive.** The class is `expensive` not `irreversible` — technically you can revert — but the consequences are non-trivial:

**If no contributors have pulled the vault commit yet** (the post-ship window before anyone else clones/pulls):
- `git revert <slice-069-commit-sha>` undoes the `.gitignore` flip + the vault add atomically
- Re-add `architecture/` to `.gitignore`
- Total cost: <15 minutes; the revert is mechanically simple

**If contributors HAVE pulled the vault commit**:
- The revert still works locally but breaks their working tree (their vault directory disappears)
- They must `git reset --hard` or `git checkout` the vault back, OR re-clone
- If they made vault edits between pull-time and revert-time, those edits are stranded
- The "vault is tracked" cultural premise has propagated; cultural revert is harder than mechanical revert

**If a secret leaked into the vault commit and the leak is discovered post-fact**:
- Standard git revert does NOT remove the secret from git history (the blob persists in `.git/objects` and is rendered visible to anyone who clones)
- Remediation requires `git filter-repo` (or BFG) to rewrite history + force-push to master + every contributor must re-clone
- Force-push to master is destructive to anyone holding a working tree; coordinator effort is high
- For public forks: the secret is permanently in their fork history regardless — the secret IS compromised

The reversibility tag reflects this conditional cost: cheap if caught immediately and the user is solo; expensive if contributors have pulled; effectively-irreversible if a secret leaked and was discovered late. The must-not-defer pre-commit secrets scan mitigates the worst case proactively.

Reversibility class **expensive**.

## Reversibility taxonomy (introduced by this ADR)

Per /critique M1 ACCEPTED-FIXED: prior ADRs use the `cheap`/`expensive`/`irreversible` labels informally without a single canonical taxonomy section. ADR-066 promotes the 3-class framework inline here so subsequent ADRs can cite this section:

- **cheap**: revert is < 1 hr of local work with no downstream coordination cost (no other contributors hold a pulled working tree of the change; no cultural premise has propagated; no derived artifact requires regeneration). Example: ADR-013 (PMI-1 v1.1 refactor, slice-014) — pure local edit revertible by `git revert` in minutes.
- **expensive**: revert is technically possible but carries downstream coordination cost (contributors must re-clone or hard-reset) OR cultural cost (a discipline has propagated and reverting requires re-teaching) OR partial-state cost (some derived artifacts are stranded by the revert and must be manually reconstructed). Example: this ADR (slice-069) — if contributors have pulled the vault commit, revert breaks their working trees.
- **irreversible**: revert is technically impossible OR destroys data OR forces a force-push to master that destroys git history. Example: a primary-entity-shape change after data has been written; a secret leak detected post-fact (the `.git/objects` blob persists in clones; force-push to master is destructive).

This taxonomy is ADR-066's own framework, not a citation of a prior ADR (the originally-cited "ADR-019 reversibility taxonomy" did not exist).

# ADR-041: One `v0.52.0` entry carries both APED-1 and MEPD-1

## Context

Slice-039 codifies two distinct Critic disciplines (APED-1, MEPD-1) in one
slice. The methodology-changelog convention is one `## vN.N.0` entry per
methodology change, with PMI-1 enforcing an atomic 4-part version bump
(`VERSION` + `~/.claude/ai-sdlc-VERSION` + `plugin.yaml.version` + forward-synced
`~/.claude/methodology-changelog.md`). Recent precedent is one rule per version
(v0.49 SRCD-1, v0.50 PTFFD-1, v0.51 SRSC-1). Two rules in one slice raises:
one version with two `Rule reference`s, or two sequential versions
(v0.52.0 APED-1 then v0.53.0 MEPD-1)?

## Options considered

1. **Two sequential versions** (v0.52.0 = APED-1, v0.53.0 = MEPD-1).
   - Pro: matches the recent one-rule-per-version cadence.
   - Con: implies a temporal ordering / dependency between the two rules that
     does not exist — they were generated by ONE `/critic-calibrate` run,
     accepted in ONE user action (2026-05-17), and applied in ONE atomic
     Critic-prompt edit cycle. Sequential versions misrepresent the history.
   - Con: doubles the PMI-1 4-part bump churn and creates two
     `## vN.N.0` headers for what is one indivisible change set (both edits
     land in the same `agents/critique.md` forward-sync; neither is shippable
     independently of the CAD-1 sync).
2. **One `v0.52.0` entry carrying both `Rule reference: APED-1` and
   `Rule reference: MEPD-1`** under a single `### Added` section listing both
   rules.
   - Pro: one atomic PMI-1 bump for one atomic change set; the changelog
     history faithfully records "these two disciplines were applied together
     from the 2026-05-17 calibration run".
   - Pro: precedent exists for a multi-ADR / multi-artifact single version
     (slice-037 v0.50.0 spans ADR-037 + ADR-038); a multi-`Rule reference`
     entry is the natural generalization.
   - Con: the entry-pin test convention is one function per rule — handled by
     having TWO entry-pin functions
     (`test_v_0_52_0_aped_1_*`, `test_v_0_52_0_mepd_1_*`) both keyed to
     v0.52.0, which the changelog-test harness already supports (multiple
     `test_v_0_NN_0_*` per version, cf. v0.40.0 / v0.41.0 / v0.42.0 each
     having both an `_entry_present` and a `_shippability_consumer_propagation`
     function).

## Decision

Adopt **Option 2**. One `## v0.52.0 — 2026-05-18` entry, one `### Added`
section, two bold rule blocks (**APED-1**, **MEPD-1**), one 4-part PMI-1 atomic
bump 0.51.0→0.52.0. Two entry-pin functions plus one
`test_v_0_52_0_critique_proposals_shippability_consumer_propagation` (the
`_lists_eleven`→`_lists_twelve` SCPD-1 assertion), all keyed to v0.52.0 under
one dedicated `# --- Slice-039 / APED-1 + MEPD-1 entry pinning ---` section
header in `tests/methodology/test_methodology_changelog.py`.

## Consequences

- One version-bump fix block; FBCD-1 cross-file harmonization scope is
  `{mission-brief.md, design.md, ADR-040, ADR-041, methodology-changelog.md,
  test_methodology_changelog.py, shippability.md}` for the single string
  `v0.52.0` / `0.52.0`.
- No PMI-1 versioned-gate is superseded this slice (PMI-1 gate tracks the
  current version; bumping 0.51.0→0.52.0 supersedes the PMI-1 gate exactly as
  every version bump does — the standard single supersession, NOT a
  two-version double supersession). EPGD-1 build-time-slip mode: the new
  entry-pins go under their own dedicated section header, structurally
  separated from the PMI-1 gate's section header (no shared intervening prose).
- Future multi-rule-in-one-slice changes follow this precedent: one version,
  multiple `Rule reference`s, one entry-pin per rule.

## Reversibility

**cheap** — versioning is a string convention in the changelog + test
function names + the shippability row + `VERSION`/`plugin.yaml`. Splitting into
two versions later (or the reverse) is a localized multi-file string edit with
PMI-1 + the entry-pin tests as the backstop. Cost ≈ 1 hour.

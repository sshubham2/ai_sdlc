# ADR-057: Seed the wakeup-prompt guardrail via an INSTALL.md → global CLAUDE.md append

## Context

The lesson "`ScheduleWakeup` replays its `prompt` argument literally as fresh
user input at fire time, so a slash-command-shaped string must never be passed
as a no-op label / heartbeat / fallback wakeup" is a real operational defect
class — experienced N=2 in recent sessions. Today it is captured only in this
machine's project memory (`memory/schedulewakeup-replays-prompt-literally.md`).
Memory is project-scoped (keyed on the cwd path); it does not travel to other
machines, nor to other projects on the same machine.

Slice-058 makes the guardrail portable. The mission brief explicitly deferred
*where the guardrail content should live* to `/design-slice` — this ADR records
that decision.

## Options considered

1. **`INSTALL.md` → global `~/.claude/CLAUDE.md` append.** A new install step,
   modelled on Step 3d (the existing PY-convention append), writes a
   `# Wakeup-prompt discipline` block to the installing user's global
   `~/.claude/CLAUDE.md`.
   - Pros: every machine that installs the pipeline inherits the rule; global
     `~/.claude/CLAUDE.md` is loaded in *every* project on that machine, so the
     guardrail reaches pipeline and non-pipeline work alike; `INSTALL.md`
     already has the exact Step 3d machinery (idempotent, diff-shown,
     confirmation-gated); consistent with [[ADR-049]]'s decided global-only
     install posture; minimal surface — one new step + one regression test.
   - Cons: couples a harness-tool-usage lesson into the pipeline installer; the
     block lands in the user's global file (mitigated — the confirmation gate
     and `INSTALL.md:198` already govern global-CLAUDE.md edits).
2. **Fold the guardrail into the per-project `CLAUDE.md` generated by
   `/triage` + `/adopt`.** Each time a project is opened/adopted, the generated
   project-root `CLAUDE.md` carries the block.
   - Pros: scoped to pipeline projects.
   - Cons: reaches only projects opened/adopted *after* the change — existing
     pipeline projects never get it; the guardrail is harness-general, not
     pipeline-specific, so per-project is the wrong granularity; it touches the
     OSDG-1-guarded `/triage` + `/adopt` `SKILL.md` surfaces (broader Critic +
     drift-guard blast radius) for *strictly less* reach than option 1, since
     global `~/.claude/CLAUDE.md` is already loaded inside pipeline projects.
3. **Both.** Redundant — anything in global `~/.claude/CLAUDE.md` is already
   loaded in pipeline projects, so option 2 adds nothing on top of option 1
   except double the surface and a second drift vector.

## Decision

**Option 1 — `INSTALL.md` → global `~/.claude/CLAUDE.md` append.**

The guardrail is a *harness-tool-usage* rule (`ScheduleWakeup` is a Claude Code
harness tool, not a pipeline operation), so global scope is the correct
granularity: it should apply to all work on a machine, not just pipeline
projects. Global `~/.claude/CLAUDE.md` is loaded in every project, so option 1
strictly dominates option 2 on reach. [[ADR-049]] already established that
install-time scope in this project is global-only; appending to global
`~/.claude/CLAUDE.md` via `INSTALL.md` is the established, decided pattern (it
is the same mechanism as Step 3d's PY-convention block). Option 2 would touch
OSDG-1-guarded opener skills for no added reach; option 3 is redundant.

[[ADR-049]] does **not** foreclose option 2 — ADR-049's "global-only" decision
concerns *artifact copy scope* (skill/agent file precedence shadowing), a
different mechanism from a generated project-root `CLAUDE.md`. Option 2 is
mechanically feasible; it is rejected on granularity and reach grounds, not
infeasibility.

## Consequences

- `INSTALL.md` gains one new idempotent, confirmation-gated step (the slice's
  AC1). `/triage` and `/adopt` are **not** touched — no OSDG-1 / drift-guard
  surface is disturbed.
- The guardrail propagates to every machine that runs `INSTALL.md`, on every
  install and re-install (idempotent skip on re-run).
- The guardrail does **not** retroactively reach machines already installed
  before slice-058 — it lands on the next `INSTALL.md` run (re-install to
  update is the documented pattern, `INSTALL.md` "Source independence").
- Per-project scoping of the guardrail remains available as future work if a
  pipeline-specific variant is ever wanted; it is not committed here.

## Reversibility

**Cheap.** The decision materializes as one prose step in `INSTALL.md` plus the
block text. Changing the placement later (e.g. moving to option 2) is a
prose-only edit with no data migration, no schema, and no code consumer to
unwind. Supersedable in the normal append-only way (SUP-1) via a future ADR.

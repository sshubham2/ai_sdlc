## Missed findings

Concerns the first Critic didn't flag but the meta-Critic surfaces from independent re-review against the LIVE repo:

- **M-add-1: The dedup rationale's "folder co-exists with the worktree in the main tree the whole in-flight period" is factually WRONG, and it invalidates what test 4n proves.** design.md §Dedup design (L123-126) and ADR-084 §Decision (L83-84, B1 parenthetical) both justify including worktree'd branches in the dedup ref-set by asserting the main-tree folder co-exists with the live worktree throughout the in-flight period ("BRANCH-2: worktree is a sibling copy; main-tree folder never removed"). I checked the live repo: this is false. Under BRANCH-2 a branched slice's folder is created **in the worktree**, not the main tree — slice-091 has a worktree + `slice/091` branch, and its folder is present in `C:/Users/sshub/ai_sdlc-wt/slice-091-.../architecture/slices/` and on the `slice/091` tree, but is **absent from the main tree's `architecture/slices/`** and **absent from `master`** (`git ls-tree -d master architecture/slices/` returns only `archive`; zero non-archive slice folders ever live on master — merged slices move to `archive/`). Consequence (per Hendrickson, *Explore It!* — test the state model you actually have, not the one you assume): when the audit runs `--repo-root .` from the **main tree** (the `/slice` consult, the R-31 target context), the folder pass scanning `architecture/slices/` never even enumerates a branched slice's folder, so the worktree-branch dedup is moot there — there is nothing to dedup. The worktree-branch dedup is load-bearing **only** in context-2 (`/build-slice` running `--repo-root .` from *inside* the worktree, where the worktree's own folder IS present alongside its branch). Test 4n (design.md L179-182) says "a worktree's own foldered+branched slice → exactly one IN-PROGRESS, zero BRANCHLESS"; if 4n runs `classify_branches(repo)` from the **main** repo root (the idiom every other case in `test_stranded_slice_audit.py` uses, e.g. `_add_live_worktree` then `classify_branches(repo)` at L184-194), it will pass *trivially* — zero BRANCHLESS because the folder was never scanned, NOT because dedup suppressed it. That makes 4n a vacuous pin for B2/context-2, the very thing it exists to prove. **Proposed fix**: (a) correct the design + ADR rationale to state the folder lives in the *worktree*, not the main tree, so the worktree-branch dedup matters only for the in-worktree (`--repo-root <wt>`) invocation; and (b) make test 4n (or the 4k worktree'd variant) run `classify_branches(wt_path)` from inside the worktree — where the folder AND the live worktree-branch coexist — so the dedup is genuinely exercised; assert `len([e for e in entries if e.klass is BRANCHLESS_IN_FLIGHT])==0` AND exactly one IN-PROGRESS for that slice. Without (b), the strongest dedup invariant ships unverified despite the B2 fix.

- **m-add-2: stage-present-frontmatter-but-no-`stage:`-field emits `vault_state="folder:None"` and is not pinned.** design.md §Error model (L214-217) says "absent or unparseable `milestone.md` → skipped," and 4m (L176-178) tests "no `milestone.md` (or unparseable frontmatter) → skipped." But I executed the reused helpers: a milestone WITH well-formed `---` frontmatter that simply omits `stage:` yields `_frontmatter_field(txt,"stage") → None`, and `_is_terminal(None, next_action) → False` (unless `next_action` matches `\bcommit\b`). So such a folder is NOT skipped (it parses fine) and NOT terminal — it emits a `BRANCHLESS_IN_FLIGHT` entry with `vault_state="folder:None"` and a `reason` naming a `None` stage (per Wiegers, *Software Requirements* — an underspecified boundary between "unparseable" and "parseable-but-incomplete"). This contradicts must-not-defer #5 ("name the branchless slice + stage so /slice AND /pulse can render it") — `folder:None` names no stage. **Proposed fix**: pin the design's "unparseable → skip" to explicitly cover stage-is-None (either skip it as unparseable, or emit `folder:unknown`/`folder:?` rather than the literal `None`), and add a one-line assertion to 4m that a frontmatter-present-but-stage-less folder produces no `folder:None` entry. Low blast (advisory output), but it is a named must-not-defer observability requirement.

## Summary
The fix is well-scoped, ADR-084 is sound, and the design correctly stays informational-never-halt in line with ADR-079 / the parallel-slice trajectory. But two real defects surface under execution: (1) a **self-surfacing** gap — the slice's own branchless scaffold (and, at /build-slice time, the worktree's own in-flight folder) will be reported by the very pass being added, which neither the repro test nor ADR-084's "different worktree" residual addresses, and (2) the **dedup key-assembly** is under-specified against the actual `WorktreeInfo` shape (`slice_name` is the bare name, not `NNN-name`), creating a concrete double-report / key-mismatch risk the design hand-waves. Plus a `/pulse` consumer-prose gap and a missing terminal-folder regression assertion in the repro layer.

## Findings

### Blockers (must address before /build-slice)

#### B1: Self-surfacing — the audit will report the invoking tree's OWN active slice folder as a branchless in-flight entry
- **Claim under review**: design.md § "Self-reference note": *"This very /slice→/design run is producing the branchless slice-092 folder the fix would surface — the bug is being designed against its own live instance."* And AC2: surface *"an `architecture/slices/slice-NNN-<name>/` folder present in the invoking tree whose `milestone.md` exists and is NON-terminal AND which has no matching `slice/NNN-*` branch."*
- **Issue**: This is treated as a cute coincidence, but it is a live correctness problem. When `/slice` runs its prereq consult **in the main tree** (the normal invocation per `skills/slice/SKILL.md` L38–41, `--repo-root .`), the new pass enumerates `architecture/slices/slice-*/` in that same tree. The slice the operator is *currently defining* — its own freshly-written non-terminal `milestone.md`, no branch yet — will match the new `BRANCHLESS_IN_FLIGHT` criteria and be surfaced as an entry **describing the operator's own in-progress action back to them**. Worse, under BRANCH-2 the normal `/build-slice` invocation runs inside a worktree whose `architecture/slices/slice-NNN-<name>/` folder is the slice being built; any tool run with `--repo-root .` there will surface the worktree's own slice as "branchless in-flight" (it has a folder, and from the worktree's local ref enumeration the dedup may or may not catch it — see B2). I confirmed empirically that the proposed folder regex `^slice-(\d{3})-(.+)$` matches `slice-092-fix-stranded-audit-branchless-blindspot` and excludes `archive` (good), so the self-match WILL fire on the real tree. This is precisely the Dim-7(b) architectural-concurrency / cry-wolf class from the calibration guidance (slice-087 flagged its own in-flight state; the user caught it). The design's only carve-out is dedup-against-branches and terminal-skip — neither excludes the invoking slice itself.
- **Evidence**: `tools/stranded_slice_audit.py` `classify_branches` L344 takes `repo_root`; `skills/slice/SKILL.md` L41 invokes `--repo-root .`; real-tree regex execution (this critique) confirms `slice-092-…` matches. ADR-084 § Consequences explicitly leaves "a branchless slice whose folder lives in a different worktree than the invoking one is not cross-scanned" as residual — but says nothing about the inverse, far more common case: the **invoking tree's own current slice**.
- **Proposed fix**: Add an explicit exclusion of the slice being currently operated on. Cleanest: exclude any folder whose `milestone.md` is the active/invoking slice — e.g., resolve the current slice (the one `/slice` or `/build-slice` is acting on) and skip its folder, OR (simpler and defensible) document + test that the branchless pass is **only meaningful when run from a tree that is NOT itself the home of the surfaced folder**, and have `/slice` filter its own just-created folder. At minimum, AC2/the design must state the rule that disambiguates "my own in-flight slice (expected, not surfaced)" from "a *sibling* branchless in-flight slice (the R-31 target)". Add a test case (4n) asserting that the invoking tree's own current-slice folder is NOT surfaced as a foreign branchless entry. Without this, every single `/slice` run post-fix surfaces the operator's own brand-new scaffold — the exact cry-wolf that motivated the slice-087 reframe.
- **Builder draft**: ACCEPTED-FIXED (design+ADR disambiguation) + ACCEPTED-PENDING (the test, applied at build). The R-31 consult itself is **timing-safe** — `skills/slice/SKILL.md` runs the stranded consult BEFORE Step 1, and the current slice's folder isn't written until Step 6, so at consult time the tool never sees its own not-yet-created folder (and DOES correctly see *sibling* branchless slices — the R-31 target). The genuine exposure is (a) `/build-slice`-in-worktree, where the worktree's own slice **has a branch**, so correct dedup (B2) suppresses it; and (b) `/pulse`/manual runs after the folder exists but before branching, where surfacing the operator's own in-flight slice is *intended* situational awareness, not cry-wolf (it IS branchless in-flight). Design + ADR-084 now state this disambiguation rule explicitly; AC adds test 4n (worktree's own foldered+branched slice → exactly one IN-PROGRESS, zero BRANCHLESS) at build. Flagged for TRI-1: if the user wants a hard "exclude folder == invoking-slice" filter beyond the timing+dedup argument, that is a larger contract (the tool would need to learn which slice is "current") — recommend the documented-rule + dedup approach.

#### B2: Dedup key assembly is under-specified against the real `WorktreeInfo` shape — worktree'd-but-branchless dedup will mis-key
- **Claim under review**: design.md § "Dedup design": *"assemble `seen_keys: set[str]` = the `NNN-name` key of every `slice/*` ref encountered — both `worktree_branches` AND the bare-branch set… Key derivation strips the `slice-`/`slice/` prefix uniformly."* And § What's reused: *"reuses the `git for-each-ref` ref set for dedup."*
- **Issue**: The design proposes deriving `seen_keys` from "`slice/*` refs encountered." But the worktree pass (`classify_branches` L364–387) keys worktrees by `wt.branch` (full `slice/NNN-name` ref) into `worktree_branches`, while the bare-branch path is the `for-each-ref refs/heads/slice/` set. The design says reuse "the `git for-each-ref` ref set" for dedup — but **`for-each-ref refs/heads/slice/` does NOT enumerate a branch that exists only as a worktree checkout if that worktree branch is also a local head** (it is — worktrees are on local branches, so it appears). However, the actual trap: the design proposes building `seen_keys` from refs, but a branchless folder by definition has NO ref. The dedup is folder-key vs branch-key. I executed the key derivation: folder `slice-092-<name>` → strip `slice-` → `092-<name>`; branch `slice/092-<name>` → strip `slice/` → `092-<name>`; **equal — good**. BUT the design's sentence "the `NNN-name` key of every `slice/*` ref" is ambiguous about whether it includes worktree'd branches assembled from `WorktreeInfo`. `WorktreeInfo.slice_name` (verified at `tools/pulse_worktree_resolver.py` L148, L323 `m.group(2)`) is the **bare name without the `NNN-` prefix** — so if the implementer reconstructs the worktree key from `wt.slice_name` alone they get `<name>` not `NNN-<name>`, and the folder key `NNN-<name>` will NOT match → the post-`/build-slice` foldered+worktree'd slice gets **double-reported** (once via the worktree pass, once via the new branchless pass), violating must-not-defer #1 and AC2. The design must pin that the worktree key is reconstructed as `f"{wt.slice_num}-{wt.slice_name}"` (using `slice_num`, L147), not from `slice_name` or `wt.branch` string-slicing alone.
- **Evidence**: `tools/pulse_worktree_resolver.py` L142–149 (`WorktreeInfo`: `slice_num` and `slice_name` are separate fields, `slice_name = m.group(2)` = name only); `classify_branches` L365 stores `wt.branch` (full ref) in `worktree_branches`, not a `NNN-name` key. Key-derivation executed in this critique confirms folder/branch keys coincide ONLY when both carry the `NNN-` prefix.
- **Proposed fix**: In design.md § Dedup design, replace the vague "every `slice/*` ref" with an explicit construction: `seen_keys = {b[len("slice/"):] for b in worktree_branches} | {f"{num}-{name}" for (_branch, num, name) in bare_branch_tuples}`. Note that `worktree_branches` holds full `slice/NNN-name` refs (so slicing `slice/` works), while the bare set yields `(branch, num, name)` tuples (so build `NNN-name` from `num`+`name`). Add test 4k to assert a foldered+**worktree'd** (not just foldered+bare) slice is reported exactly once — the design's 4k only covers foldered+bare per the test-plan line "4k dedup vs branch."
- **Builder draft**: ACCEPTED-FIXED — design.md § Dedup design updated to pin the exact key construction (worktree refs via `b[len("slice/"):]`; bare via `f"{num}-{name}"`; folder via regex capture `f"{num}-{name}"`), explicitly forbidding the `wt.slice_name`-alone derivation. Test 4k extended at build to cover the foldered+**worktree'd** case (not only foldered+bare), asserting exactly one entry.

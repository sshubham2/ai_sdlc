## Missed findings

- **M-add-1 (Major): the M1 cross-tree `git show <branch>:…/milestone.md` lookup reads COMMITTED branch state only, but a slice's milestone is frequently UNCOMMITTED in its working tree — a stale-read mislabel in the exact bare-branch case M1 governs.** The M1 fix (design.md §What's-new, ADR-079, mission-brief AC4(a)) reads the branch's own tree via `git ls-tree`/`git show <branch>:`. Both read only **committed** tip state. Verified live: slice/088's committed milestone is `stage: slice` while its working-tree milestone is `stage: design` (`git diff HEAD` shows the milestone + mission-brief + design + critique + ADR-080 all uncommitted). For a branch WITH a worktree this is masked (precedence #2's `classify_worktree_state` reads the working-tree `milestone_path`, `pulse_worktree_resolver.py:331-334`). But the bare-branch (no-worktree) path is exactly where M1 applies, and there `git show <branch>:` is the only source. The benign sub-case is the canonical slice-086 incident (archive committed before the worktree died). The adversarial sub-case the design did not address: a worktree removed (partial `--merge` cleanup, R-22 lineage) *after* reflect/archive on disk but *before* that terminal milestone/`archive/` move was committed → `git show <branch>:` returns a pre-reflect/pre-archive stage → STRANDED-COMPLETE silently downgrades to IN-PROGRESS or ORPHANED → weakened/absent halt. **Major, not Minor**, because it silently *weakens the halt* on a genuine-divergence branch — the precise failure class this slice exists to close. **Proposed fix**: state explicitly in the error model that the bare-branch `git show <branch>:` read is committed-tip and may lag uncommitted working-tree state; minimum bar is to NAME the staleness so the Builder doesn't assume `git show` is ground truth; optionally add a dirty-worktree-at-removal caveat.

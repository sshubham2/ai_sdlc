## Suspicious findings

- **B1: "the breaker count is 99, not 74" — SUSPICIOUS (wrong-simulation measurement).** The first Critic measured `99 failed / methodology 91` against an **empty** external vault dir (no seeded copy). Post-real-flip the external store IS seeded (the flip moves content, it does not delete it), so those ~17 are ALREADY CORRECT post-flip and need no fix.

  The first Critic was directionally right that "74" had drifted, but it overcorrected to a number from a **non-representative** simulation, and the Builder then wrote "~99 / 91 methodology" into mission-brief AC1 + design.md:21 alongside a gate defined as SEEDED — an internal inconsistency. Worse, design.md:21 rationalizes the ~17 delta as "the env-sim superset ... fixed for robustness (defense-in-depth)," but "fixing" `test_live_repo_self_application_clean` to pass against an EMPTY vault would **break its purpose** (it must read real content).   Recommend: reframe the count to **~82 full / ~74 methodology, measured against a SEEDED external copy** (the real-flip-faithful sim), and STRIKE the "defense-in-depth superset" framing for the ~17 content-dependent audits. The AC1 "re-measure live at build" instruction survives — but the build MUST seed the external copy (per AC1's own wording), or it will chase ~17 phantom breakers. (The finding is still ACCEPTED-PENDING-class — the count IS re-measured at build — but the design must not anchor the build to the empty-sim number, and the verification plan's "red today (~99)" in row 1 is wrong for the seeded gate it defines.)

The first Critic's pattern this slice is **precise-on-code-paths but mis-calibrated-on-the-one-number-that-was-executed** — an ironic inversion of the usual APED-1 win, since the executed measurement (B1) used a non-representative simulation while the un-executed reasoning (B2/B3/M1) was sound.

On the highest-value question the prompt posed — **is the AC2-narrowing / prep-flip boundary sound, or does the deferral re-create the bootstrap problem that BLOCKED the flip?** — my verdict is: the boundary is drawn in a **defensible** place but the mission-brief's "suite-neutral no-op" framing over-claims. The prep correctly routes the genuinely-flip-safe ops (drift-log.md and the shared-aggregate `vault_edit --file` writes are VAULT_ROOT-relative and flip-safe; the archive `mv` destination is canonical) and correctly defers the genuinely-bootstrap-entangled per-slice active-folder writes — those depend on the worktree-vs-external decision (today slice content rides the git no-ff merge into the canonical vault; post-flip it must instead write to the external store), which is legitimately the flip slice's to own. The deferral does NOT re-create the original BLOCK, because the original block was caused by deferring the fix to a SEPARATE later slice (slice-111) that ran AFTER the flip slice's own `/reflect`; here the active-folder routing lands IN the flip slice alongside the move, so the flip slice can sequence its own `/reflect` correctly. BUT two residual risks survive into the flip and must be visible at TRI-1: (1) routing the archive-`mv` DESTINATION to external NOW while the active-folder SOURCE stays worktree-local creates a cross-store `mv` whose coherence depends on the very bootstrap decision being deferred — verify at build that the routed `mv` is coherent with an un-routed source; and (2) per M-add-2, the deferred writes must remain GATE-VISIBLE (not baselined-silent), or "the flip is a no-op" becomes "the flip ships with a green gate over a half-routed pipeline." My one reservation: the M1 worktree-RETIRE test fix (pin own vault root) makes the suite location-agnostic correctly, but the production path it covers (`classify_worktree_state` reading the worktree milestone via VAULT_ROOT) is itself part of the deferred bootstrap — so the green test could mask that worktree-milestone resolution is not yet flip-correct; that is arguably in-scope-acceptable for a prep whose job is suite-neutrality, but the flip slice's reviewer should not read that green test as flip-readiness evidence for worktree resolution.

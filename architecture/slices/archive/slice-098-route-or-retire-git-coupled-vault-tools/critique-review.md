## Missed findings

Concerns the first Critic didn't flag and that the Builder's r2 fixes did not close — surfaced by adversarially re-attacking the r2 fixes per the "a Builder's own fix is a fresh claim" mandate:

- **M-add-1 (Major): the B2/M2-fix guard-placement claim is contradicted by PCR's real control flow — the named Class-B `_git_show_stage` reads (L216-217) fire UPSTREAM of `resolve_soft_conflict`, inside `diagnose_conflict`.** design.md §components-PCR and the per-site table list `_git_show_stage` reads "L216-217/…" as RETIRE-when-untracked with "guard fires at entry to `resolve_soft_conflict`/`resolve_vault_claim_conflict`." But L216-217 is inside `diagnose_conflict` (L193), which `main` calls unconditionally at L2287 for EVERY mode — structurally *before* `resolve_soft_conflict` (L302) is reached, and even before `classify_conflict`. A guard placed "at entry to `resolve_soft_conflict`" cannot protect L216-217. The design conflates two different Class-B read sites (the diagnose-time reads at L216-217 vs the equivalence-guard reads at L1967-1968/2056-2057) under one guard location that only covers the latter. **The save the design relies on but never states**: a genuinely untracked vault is not git-tracked, so `git status --porcelain` (L781-788) never emits it as a U-file → `diag.u_files` excludes `architecture/slice-queue.md` → `classify_conflict` returns UNKNOWN (L277-278) → L216-217 is never reached. This is real and load-bearing, but it means the binding mechanism for the diagnose-time reads is the **empty-U-file → UNKNOWN fall-through**, NOT the resolve-entry tracked-check guard the design names. Per McGraw (place the check at the actual trust boundary) and APED-1 (execute, don't reason): the design must either (a) state that the diagnose-time Class-B reads are protected by the U-file-absence → UNKNOWN path and add a test that an untracked vault yields zero U-files (no `_git_show_stage` call ever fires), or (b) add the tracked-check at `diagnose_conflict` entry too. As written, AC5's "before composing any out_path/relative_to" is satisfied for the write path but the *named* read sites L216-217 are guarded by a different mechanism than claimed.

- **M-add-2 (Major): stranded's `archive_path`/`milestone_path` are single variables consumed in BOTH a Class-A and a Class-B position — the two-literal-class model partitions *literals*, but these literals have two classes at once.** At `tools/stranded_slice_audit.py` L301 `archive_path = f"architecture/slices/archive/slice-{num}-{name}"` and L307 `milestone_path = f"architecture/slices/slice-{num}-{name}/milestone.md"` are each used as (i) a Class-B git pathspec — `_branch_tree_has_path(repo_root, branch, archive_path)` L302 (ls-tree) and `_branch_tree_file(repo_root, branch, milestone_path)` L308 (show), AND (ii) a Class-A filesystem operand — `(repo_root / archive_path).exists()` L322 and `repo_root / milestone_path` L327. The design (per-site table) assigns L322/L327 to ROUTE (Class A) and L301/L307→L302/L308 to RETIRE-when-untracked (Class B), but it is the *same string object*. You cannot route the variable for the filesystem fallback without also feeding the routed form into the git pathspec (or vice versa) unless you derive two separate values. The design never states that the build must split these into a routed filesystem path AND a preserved forward-slash git pathspec. Per Fowler (a value that serves two contracts must be materialized twice). Proposed fix: design must specify that L301/L307 yield two derivations — a forward-slash repo-relative string kept for the git pathspec (L302/L308) and a separately ROUTE-composed `VAULT_ROOT`-rooted Path for the filesystem fallback (L322/L327) — and a test that the external-untracked path exercises both branches.

- **M-add-3 (Major, refines M5): the stated AST predicate ("string-constant used as an operand of `Path.__truediv__`") cannot match the real Class-A site at L322, because the operand there is a *variable* (`archive_path`), not a string constant — the literal is assigned first (L301), then joined.** design.md §AST-predicate pins absence "only in Class-A positions: a string-constant used as an operand of `Path.__truediv__`." But `(repo_root / archive_path).exists()` (L322) has a *Name* node (`archive_path`) as the rhs operand, not a `Constant`. The `architecture/...` string literal lives at the f-string assignment L301, which is neither a `Path.__truediv__` operand nor (after r2 routing) something the allowlist names. So the scan as specified would (a) not flag L322 as an un-routed Class-A site even if the Builder forgot to route it (false-negative → vacuity risk the M5 fix was supposed to close), and (b) potentially flag the L301 f-string under the docstring/git-identity allowlist ambiguously. The same shape recurs at PCR `qrel = "architecture/slice-queue.md"` (L1965) — a literal assigned to a variable then string-compared. Per the slice-092 mutation lesson the design cites: the mutation test ("re-introduce one routed Class-A literal → scan FAILS") must mutate a *variable-mediated* site like L322, not only a direct `repo_root / "architecture" / "x"` literal, or the non-vacuity proof is itself vacuous for the hardest real case. Proposed fix: extend the predicate to track Class-A through one level of local-variable assignment (def-use of an f-string/str-literal `architecture/...` Name later used as a `Path.__truediv__` operand against repo_root/scan_root), and mutate L322 (variable-mediated) in the non-vacuity proof.

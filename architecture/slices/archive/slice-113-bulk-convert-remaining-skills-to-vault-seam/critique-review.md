## Missed findings

- **M-add-1 (Blocker): the OSDG-1 forward-sync SET is wrong — converts `code-review`/`pulse` without syncing them, lists `diagnose` which has no drift test.** The design (design.md §"~/.claude/skills ×12 guarded forward-sync") and mission-brief AC#3 enumerate exactly 12 skills: slice, build-slice, commit-slice, query-design, critique, **diagnose**, design-slice, critique-review, triage, adopt, reflect, slice-candidates. The ACTUAL `*_skill_drift` test set is **13**: those 12 minus `diagnose` (there is NO `test_diagnose_skill_drift.py` — only `test_diagnose_skill.py` / `test_diagnose_pass_models.py` / `test_diagnose_narrator_agent.py`), PLUS `test_code_review_skill_drift.py` and `test_pulse_skill_drift.py`. Both code-review (47 convertible occurrences incl. `architecture/triage.md`, `architecture/risk-register.md`, `architecture/shippability.md`) and pulse (16 convertible occurrences incl. `architecture/concept.md`, `architecture/risk-register.md`, `architecture/shippability.md`) are squarely in the bulk-conversion scope. `test_pulse_skill_drift.py:39` and `test_code_review_skill_drift.py` assert WHOLE-FILE content-equality (`assert_md_forward_synced`) between in-repo and installed. Converting either in-repo without force-syncing it to `~/.claude/` REDS that drift test at finish — directly violating AC#3 ("*_skill_drift tests pass") and the must-not-defer ("OSDG-1 forward-sync of every converted guarded SKILL.md"). Per the project's own CLAUDE.md self-hosting note, "pulse + code-review have drift tests but are not yet enumerated [in the OSDG-1 list]" — the design author appears to have worked from that stale 12-member prose enumeration rather than the on-disk test set (Sommerville — configuration-item completeness; the governed set is the tests on disk, not the prose roster). Proposed fix: replace the design's forward-sync roster with the on-disk `tests/methodology/*_skill_drift.py` set computed at build (drop `diagnose`, add `code-review` + `pulse`), force-sync all 13 converted+guarded copies, and assert `pytest tests/methodology -k skill_drift` green (this is also what m2's widened smoke must cover). Blocker because it is a finish-gate red that the design's enumeration structurally cannot catch.

- **M-add-2 (Major): second hard-pinned git-pathspec consumer — `tests/skills/code_review/test_code_review_skill.py:241-275` — not enumerated, and the "convert, Claude-substitutes" disposition is unsafe for pathspecs.** The first Critic's m1 caught the code-review.md:103 5-match COUNT pin in `test_vault_flip_prose_inventory.py`, but a SEPARATE test asserts the pathspec literals by VALUE: `test_code_review_skill.py:241-250` hard-asserts 10 surgical exclusion literals (`"':(exclude)architecture/decisions/**'"`, `"':(glob,exclude)architecture/*.md'"`, `"':(exclude)architecture/slices/_index.md'"`, `"':(exclude)architecture/slices/archive/**'"`, … through `code-review.md`) and `:266/272/275` assert the catch-all `':(exclude)architecture/**'` is ABSENT. Converting code-review's pathspecs breaks 10+ assertion sites. Deeper than the consumer count, m1's Builder-draft disposition ("git-pathspec → convert, Claude-substitutes") is questionable for THIS literal class: a `:(exclude)architecture/decisions/**` pathspec is consumed by `git ls-files`, NOT by Claude-as-resolver — rewriting it to `:(exclude)<vault>/decisions/**` produces an invalid runtime pathspec (git would match a literal `<vault>` dir, silently changing the exclusion set). Per ADR-105's own class taxonomy this looks like a class-1/definitional command-literal, not a convertible operational reference (Newman — a contract/interface literal consumed by an external tool must survive the seam unchanged). Proposed fix: enumerate `test_code_review_skill.py` in the consumer set alongside B1/M2; and before adopting m1's "convert" disposition, decide explicitly whether git-pathspec literals are class-1 carve-outs (likely yes, since git — not the `<vault>` resolver — consumes them) — if carved out, m1's 5-match pin and this test BOTH stay green untouched, which is the simpler and safer outcome.

## Severity adjustments

- **M3** (`_CONVERTED_CARVEOUTS` keying collision) — borderline SEVERITY-WRONG: filed as Major, defensibly Minor. The collision is mechanically real (verified: identical SHA-256 for class-4 `<wt_path>/…` and a bare same-suffix convertible) but is a LATENT ratchet-robustness weakness, not a current break — it bites only if (a) a converted file carries a class-4 `<wt_path>/architecture/X` carve-out AND (b) X later regresses as a bare `architecture/X` literal in that same file AND (c) the suffix happens to collide. No current corpus file triggers it (slice/SKILL.md is the only candidate joining `_CONVERTED_FILES` with a `<wt_path>/` literal). I do not insist on the downgrade — the Builder draft (build-time collision check + 5-tuple strengthening for any colliding file) is cheap and correct — but the user should know M3 is a hardening, not a fix, when triaging it against the genuine Blockers (B1/B2/M-add-1).

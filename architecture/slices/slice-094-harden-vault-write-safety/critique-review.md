## Suspicious findings

- **B1 (append-loss half): PARTIALLY SUSPICIOUS — the "not reliably non-vacuous" verdict is over-broad.** The first Critic (critique.md B1) asserts append-loss "flakily passes even unlocked → not reliably non-vacuous" citing "`O_APPEND` single-write atomic (#15723)." Over-reach for large payloads: `safe_append_text` does `os.write(fd, data)` (`_vault_write.py:129,150`); web-confirmed against the very bug cited, on Windows the max atomic write is ~1024 bytes and **writes >1024 bytes corrupt under concurrency even via raw `os.write`** (#15723, resolved "not a bug" = OS behavior). So a >1024-byte concurrent-append test IS non-vacuous. The Critic cited the 1024 caveat in its web-dimension then dismissed it in the B1 body — internal inconsistency. **Disposition guidance**: B1's EPERM-on-`os.replace` primary mutation is VALID (the torn-write-via-`os.replace`-atomicity half IS genuinely vacuous — `_vault_write.py:108` `os.replace` is OS-atomic); the append-half must be **re-stated**: not "append-loss vacuous," but "small-payload (≤1024B) append-loss vacuous; the non-vacuous append proof requires a >1024-byte payload." Make the >1024-byte append-interleaving check **MANDATORY** (not "if reproducible" — it is reproducible by OS guarantee; it is the only direct proof `safe_append_text` protects the append-log class). slice-093's "26/30 lost" used ~10-byte lines under THREADS with the lock disabled — a different mechanism, so they don't directly reconcile; the >1024 path is the principled non-vacuity source.
